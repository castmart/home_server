# Upgrading Immich safely

Immich follows semantic versioning: breaking changes land in major releases, and
the server is only compatible with its own major version. This repo therefore
pins one exact release in `.env` (`IMMICH_VERSION`) instead of following
`release` or a floating `v3` metatag, so an upgrade is always a deliberate,
reviewable change.

This is the procedure that took this setup from `v2.7.5` to `v3.3.5`. It applies
to any future bump; the version-specific details are collected at the end.

Everything below runs on the server, in the directory that holds
`docker-compose.yaml` and `.env`. Locally you edit the repo and ship it with
`make copy-to-host` / `make sync-to-host`.

## Before you start

- Read the release notes of **every major version you cross**, plus the
  [list of releases with breaking changes](https://github.com/immich-app/immich/discussions?discussions_q=label%3Achangelog%3Abreaking-change+sort%3Adate_created). Most
  breaking changes are API-level and only affect third-party tools, but the
  deployment-level ones are the ones that bite.
- **Upgrade the mobile apps first.** The app works with the current and the
  previous major version; the server only with its own. Upgrading phones first
  keeps backups working while the server moves.
- **Downgrading is not supported**, not even between patch releases. A rollback
  means restoring the dump you take in step 2 — which is why step 2 is not
  optional.
- Once the database runs VectorChord, never go back below Immich `v1.133.0`.

## 1. Record what is running

```bash
grep IMMICH_VERSION .env
docker compose ps
docker compose exec database psql -U immich -d immich -c '\dx'
```

The extension list should contain `vchord`. If it still shows `vectors`
(pgvecto.rs) as the active vector extension, do the
[VectorChord migration](https://docs.immich.app/install/upgrading/#migrating-to-vectorchord)
**before** moving to v3 — v3 dropped pgvecto.rs support entirely.

## 2. Back up the database and the originals

The database holds every file path and all metadata; Immich never rescans the
library folder. A copy of the photos alone cannot be restored.

Stop the server first so the dump and the files cannot drift apart:

```bash
docker compose stop immich-server
mkdir -p ~/immich-backup
docker exec -t immich_postgres pg_dump --clean --if-exists \
  --dbname=immich --username=immich \
  | gzip > ~/immich-backup/immich-$(date +%F)-pre-upgrade.sql.gz
gunzip -t ~/immich-backup/immich-$(date +%F)-pre-upgrade.sql.gz && echo "dump OK"
```

If stopping the server is not an option, dump the database **first** and copy the
files second: then the worst case is files the database does not know about,
which can be re-uploaded, instead of rows pointing at files that were never
backed up.

The critical originals live in `UPLOAD_LOCATION/{library,upload,profile}`;
`thumbs/` and `encoded-video/` can be regenerated by re-running the thumbnail
and transcoding jobs. Immich's own nightly dumps in `UPLOAD_LOCATION/backups`
are metadata only and are no substitute for either half of this step.

Do not copy `immich/pgdata` while Postgres is running and call it a backup — a
file-level copy of a live cluster is not consistent.

## 3. Diff this compose file against the release's

Upstream changes image names, digests and even the set of services between
releases. Compare before pulling:

```bash
curl -fsSL -o /tmp/immich-target.yml \
  https://github.com/immich-app/immich/releases/download/v3.3.5/docker-compose.yml
diff -u /tmp/immich-target.yml docker-compose.yaml
```

Only the Immich services matter here — Pi-hole, Kavita, Syncthing and
`cloudflared` live in the same file and will show up as differences. Carry over
anything structural: new or removed services, changed container paths, new
environment variables, new image digests.

## 4. Pin the new version

```bash
# .env
IMMICH_VERSION=v3.3.5
```

Keep `.env.example` in the repo in step with it, and remember `.env` is
gitignored: the server's copy has to be updated too (`make copy-to-host`).

## 5. Pull and start

```bash
docker compose pull
docker compose up -d --remove-orphans
```

`--remove-orphans` is what clears containers that the new compose file no longer
defines — this is how the old `immich_microservices` container goes away. Without
it, a stale container keeps running against the new database.

## 6. Let the migrations finish

```bash
docker compose logs -f immich-server
```

The first start after a major upgrade runs schema migrations. On a VectorChord
database the logs can sit on `Reindexing clip_index` and `Reindexing face_index`
for minutes on a large library — that is work in progress, not a hang. Do not
restart or `docker compose down` while migrations are running.

## 7. Verify before calling it done

```bash
docker compose ps                          # every Immich container healthy
curl -fsS localhost:2283/api/server/version   # version reported by the server
curl -fsS localhost:2283/api/server/ping      # {"res":"pong"}
```

Then, in the web UI:

- the version in **Administration** matches the pin,
- a search returns results and a photo and a video both open,
- **Administration → Job Queues** shows no failed jobs,
- machine learning (started separately from `docker-compose-ml-host.yaml`, on
  the same `IMMICH_VERSION`) answers for Smart Search and Face Detection.

Old images can be reclaimed afterwards with `docker image prune`.

## Rollback

Restoring means replacing the database with the dump from step 2 — the photos in
`UPLOAD_LOCATION` are never touched by it. The Immich restore path needs a
database that has never been migrated by the newer server, so the cluster
directory has to go. Note the service names: a blanket `docker compose down -v`
would also take down Pi-hole, Kavita and Syncthing.

```bash
docker compose rm -sf immich-server redis database
rm -rf ./immich/pgdata                 # CAUTION: wipes the database only
# put the previous IMMICH_VERSION back in .env
docker compose create immich-server redis database
docker start immich_postgres
sleep 10
gunzip --stdout ~/immich-backup/immich-<date>-pre-upgrade.sql.gz \
  | sed "s/SELECT pg_catalog.set_config('search_path', '', false);/SELECT pg_catalog.set_config('search_path', 'public, pg_catalog', true);/g" \
  | docker exec -i immich_postgres psql --dbname=immich --username=immich \
      --single-transaction --set ON_ERROR_STOP=on
docker compose up -d
```

If the server starts and runs migrations before the restore finishes, set
`DB_SKIP_MIGRATIONS=true` in `.env` for the restore and remove it afterwards.

## What the v2.7.5 → v3.3.5 bump changed here

| Change | Why |
|--------|-----|
| `immich-microservices` service removed | Background workers run inside `immich-server`; `start.sh microservices` is gone. Cleared with `up -d --remove-orphans`. |
| Server media mount `/usr/src/app/upload` → `/data` | Current container path for the media root. The host directory (`UPLOAD_LOCATION`) and its layout are unchanged. |
| `/etc/localtime:/etc/localtime:ro` mounted | Matches upstream; keeps container timestamps on host local time. |
| `redis:6.2-alpine` → `docker.io/valkey/valkey:9`, pinned by digest | What upstream ships. Still reached as `redis` and still speaks the Redis protocol, so the container keeps the name `immich_redis`. |
| Postgres image pinned by digest, `POSTGRES_INITDB_ARGS: '--data-checksums'` added | Matches upstream. The image tag itself was already the VectorChord one, so no vector-extension migration was needed; `--data-checksums` only applies to a freshly initialised cluster. |
| `DB_DATA_LOCATION` introduced | The database path is configuration, not a hardcoded mount. Default `./immich/pgdata` keeps the existing data in place. |
| `healthcheck: disable: false` on server, database and Valkey | The images ship their own health checks; enabling them makes `docker compose ps` meaningful. |
| `IMMICH_VERSION` `v2.7.5` → `v3.3.5` | The upgrade itself. |

One v3 detail worth knowing after the fact: assets imported before v3 need a
**Metadata Extraction** re-run before real-time (HLS) transcoding will work for
them. That feature is a preview and off by default.
